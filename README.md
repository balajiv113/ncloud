# ncloud

A single Flutter app for Android and iOS, bringing Nextcloud photos and files into a modern, private interface. **Early functional preview, not full Immich/Google Drive parity.** It connects directly to your server; there is no ncloud backend or telemetry.

## Development policy and architecture

**Until the app is stable, backward compatibility is not a requirement.** Remove obsolete models, aliases, cache formats and migration paths rather than preserving old preview behavior. Preview upgrades may require reconnecting or rebuilding disposable metadata; never delete server files or current-format offline downloads as part of a metadata reset.

UI widgets consume application/domain models and controller operations, not Nextcloud endpoints, DAV paths or authentication headers. `CloudBackend` defines server operations; `NextcloudClient` implements the current adapter and is selected in `main.dart`. A different server implements that contract, including its own authentication, media sources and optional discovery/change hints, without adding server-specific branches to widgets. Folder transfers and change monitoring use the same backend contract.

Async file resolution and previews are scoped to their initiating session. Clearing the preview cache invalidates in-flight results as well as stored entries; late responses cannot refill it. Resuming browsing starts a current change check instead of publishing a failure from the previous inactive session.

Initial and subsequent listing pages are checked against the initiating account and view generation before merging. Original downloads must match the listed byte count; offline saves additionally request the inventoried server revision. Failed transfers are not published as saved originals, and the transfer lock remains held through offline-file and membership publication.

Clearing browsing metadata also invalidates in-flight folder, index and path-resolution work. Late Timeline failures from a previous destination do not replace the current view's error state or discard its queued date requests. Disposed controllers cannot restore a saved login.

Pull-to-refresh keeps cached albums, folders, photos and the Timeline date index visible and usable until their replacements arrive. An explicit refresh bypasses folder-list freshness shortcuts and supersedes older discovery requests; successful responses reconcile removals as well as additions. Refresh errors keep existing content with an error notice. People previews are revision-checked and revalidated after catalogue refresh; removed people and missing face previews are purged from memory and disk rather than displayed indefinitely.

People discovery verifies Memories clusters against the Recognize DAV collection used by Photos → People. A cluster absent from Photos is not shown just because Memories still returns it. DAV verification failures surface as refresh errors, not an unverified replacement list; servers requiring a Recognize API key are authenticated through Memories' API-key endpoint.

`media_listing.dart` owns cached listing membership/paging, and `timeline_scrubber.dart` owns scrolling gestures and accessibility. The scrubber remains available to screen readers while visually hidden, with date announcements and increase/decrease actions.

## Release readiness and support

This remains a preview, not a production-certified release. Production acceptance requires device evidence for interrupted/conflicting transfers and offline preservation, first login/reconnect through the actual OIDC deployment, signed builds/upgrades, background lifecycle behavior, and profile-mode startup/frame/memory measurements on supported Android and iOS devices. A static security review and passing tests do not replace these gates.

Settings → **Support diagnostics** shows at most 40 failures from the current process. Only UTC time, a fixed failure category and an optional HTTP status are kept in memory. Exception messages, stack traces, filenames, server addresses and credentials are not captured. Nothing is uploaded; **Copy** is explicit, **Clear** removes the events, and disconnect/restart clears them. This is diagnostic information, not a durable audit log.

Regression checks include viewport-limited construction for a million-photo timeline, bounded encoded-preview memory, and 10,000 random index lookups across 100,000 dates (10.1 million timeline entries). The lookup test reports host elapsed time with a generous 10-second regression ceiling; it is not a mobile frame-rate or startup benchmark. Run `flutter test test/timeline_layout_test.dart test/preview_test.dart` for these checks and `flutter analyze` plus `flutter test` before release.

CI runs shared Dart/API checks, Android builds and iOS simulator checks independently. Both platforms execute the same `integration_test/mobile_test.dart` fixture and `test_driver/mobile_test.dart` driver: real native staging/discard, typed network/power conditions, account locks, nested Drive navigation, empty folders and persistent SQLite reopen without refetching folder listings. Android additionally checks headless engines and foreground-service lifecycle; iOS additionally checks PhotoKit, scene lifecycle, permission UI and background scheduling. Native implementations retain focused OS-specific unit tests rather than duplicating the shared Dart contract.

Android CI shares Gradle dependencies, Flutter/pub caches and SDK packages between release and device-check builds. Trusted debug builds save their own Gradle outputs; PRs read without writing that cache. The SDK cache derives its NDK and platform versions from the pinned Flutter SDK and includes CMake 3.22.1/build-tools 35.0.0; update those explicit versions when changing the Android Gradle toolchain. Cached SDK destinations are made writable before restoration to avoid root-owned preinstalled packages breaking tar extraction. The emulator job separately caches its API 35 Google APIs x86_64 system image. SDK packages are saved immediately after installation so later build failures do not discard the download cache.

Keep previews labeled as previews and use the existing private preview distribution until the device acceptance gates and production signing are complete. Preview metadata may be rebuilt without migration; originals on the server and current-format offline downloads must remain intact. Bug reports should include the app version, platform, reproduction steps and an explicitly copied diagnostic summary, not credentials or private photos.

## Install and try on Android

1. Sign in to GitHub with access to this private repository. Open **Releases** and choose the newest **ncloud Android preview**.
2. Download `ncloud-android.apk` on your phone. Open it and allow installation from your browser/file manager when Android asks.
3. Open **ncloud → Try demo** to explore immediately without an account. Demo illustrations and changes are local and reset when leaving demo.
4. To use your own files, leave demo from Settings and enter your server's full **HTTPS** address (including any Nextcloud subfolder). Choose **Connect server**, approve access in your browser, then return to ncloud.

If browser login is unavailable, create an **app password** in Nextcloud → Personal settings → Security and use the alternative sign-in form. Do not enter your main password. Self-signed/untrusted certificates and plain HTTP are intentionally not supported; install a valid certificate.

Browser approval keeps its one-time credential exchange while retrying temporary connection or account-verification failures, including authentication errors carried inside an HTTP 200 OCS response. Polling pauses while the app is backgrounded for browser approval and resumes on return; interrupted background requests do not consume the foreground retry budget. Retries are bounded and permanent failures remain visible. A Cloudflare Access deployment must allow the app's API traffic; browser cookies are not copied into the app and cross-origin redirects are not followed with credentials.

Every successful `main` build publishes an APK to a private prerelease and retains an Actions artifact for 30 days. Preview APKs use a **cached development signing key, not production signing**. If the cache expires and Android rejects an update because its signer changed, uninstall the old preview first (this clears its saved account), then install the new one. Do not distribute these builds as production releases.

## People and Map (feature branch)

On `feature/people-map`, Albums shows **People directly below Smart albums** as round face bubbles with names and photo counts, sorted by most photos first (including unnamed groups). **View all** opens a searchable People grid in the same compact navigation. Tapping a person opens the existing lazy photo grid and viewer; Back preserves the expanded People section. People covers and metadata are cache-first, revalidated in the background, and kept visible on refresh failures. People uses your account-wide Recognize results, independently of the Smart albums source folder.

**Map is separate and library-wide: all photos with saved coordinates, never a map per person.** Open it from Albums, pan or zoom to load only the visible area's server-side clusters, and tap pins to zoom closer. **Open photos in this area** opens the same lazy photo grid and viewer as the Timeline. Date counts, paging and scrubbing retain the map bounds, including views crossing the antimeridian. Photos and thumbnails continue to use your Nextcloud and the existing cache.

The map works with photo pins before loading a background. **Load OpenStreetMap background** is opt-in on each visit: tiles reveal your IP address and the viewed map area to OpenStreetMap, but never send photos, person filters or Nextcloud credentials. Attribution remains visible, and background failures do not remove your photo pins. No tiles are prefetched or downloaded offline.

An empty result, missing endpoint, disabled Recognize installation and authentication/server failure remain distinct. Geographic data and server responses are validated; map bounds use `south,north,west,east`, with wrapped viewports split into non-wrapping requests. The integration targets Memories' Recognize backend, not the separate Face Recognition app. API-contract tests use responses based on Memories 7.8.2. No new recognition jobs, face uploads, renaming or GPS edits are performed.

Local compatibility verification uses Nextcloud 32, Memories 7.8.2 and Recognize 10 with face recognition enabled. An issued app password was used to verify the People endpoint (empty groups), map initialization, real GPS clusters, geographic date/detail filters and opening an area through the controller. Face-cover cropping and nonempty person groups are covered by contract tests, not by running the recognition pipeline. The optional `test/live_discovery_test.dart` requires `LIVE_DISCOVERY=true`, `NEXTCLOUD_TEST_PASSWORD` and an isolated localhost fixture with 202 photos at latitude 45, longitude 9. Normal app sign-in still requires HTTPS.

## 0.5.5: instant timeline

The app has three destinations: **Timeline**, **Albums**, and **Drive**. Compact floating headers, a tight edge-to-edge timeline, lightweight date headers and a floating navigation pill keep content in focus. Search lives in the header; filters, sort and 2–6-column density live in **View options**. Pinching keeps the current photo row in view. On long timelines, press and drag the right edge in one gesture to scrub through the entire library, with a month bubble and year markers during dragging. The handle also appears during scrolling and fades away when idle; no separate activation press is needed.

Destination changes use directional fade/slide motion and retain each destination's scroll position; reduced-motion settings disable the animation. Swipe horizontally between Timeline, Albums and Drive at their top level. Swipes are disabled in nested views, search, selection and multi-touch interactions so they do not steal folder navigation, selection or pinch gestures. The leading title shows **ncloud** at the top level and the current folder/album in nested views; Drive has no duplicate body heading. The scrubber's hidden 48-pixel edge target remains stable throughout a gesture so revealing the handle never requires releasing and pressing again.

- **Instant thumbnails:** thumbnails are cache-first. Cached ones paint on the first frame from memory (64 MiB) or disk; tiles without one show a calm tinted placeholder (never a spinner) and fade in. Each cached thumbnail records the file revision; after an edit the previous thumbnail stays visible while the new one loads (hot update). With Memories, visible tiles are fetched together through its `multipreview` endpoint, newest requests first, and tiles scrolled past are dropped from the queue; otherwise up to four single previews load at a time.
- **Ahead-of-scroll caching:** the three-year preparation covers metadata, not every thumbnail. With persistent caching enabled, recent loaded Timeline photos now continue priming thumbnails in background batches of 48, beyond the first 60. These batches pause for metadata loading and outside the Timeline; visible tiles reuse the same requests. Prefetch work is bounded to the shared store's 40,000-file limit. Thumbnails share the 500 MiB browsing budget with library metadata. A first visit to uncached photos can still show tinted tiles; returning to cached ones does not require another download. Indexed background metadata fetching no longer shows a page-level loading bar.
- **Photo transitions:** opening a photo uses a brief fade rather than a full-screen slide and stretching Hero flight. The viewer keeps the grid's cached thumbnail visible until its larger preview arrives; reduced-motion settings disable the route animation. Opening a cached folder also retains its known photos instead of first publishing an empty loading frame.
- **Pathless timeline:** the main Timeline is painted directly from Memories day rows (id, name, type, size, revision, capture day) in batches of up to 1,500 photos, without waiting for WebDAV path lookups. Real paths are resolved on demand; actions such as open, download, share, move or offline wait for the path first. Album views still resolve paths up front for their sub-folder chips.
- **Welcome warm-up:** only sessions without a usable cached Timeline or a completed preparation marker show the preparation screen. Reopening a cached library (even a partially prepared one) never briefly switches through preparation; missing pages continue loading on demand. A first uncached sign-in loads the day index, metadata for the last 3 years and the first screens of thumbnails with real progress. **Start browsing now** skips the screen without cancelling preparation; a separate 30-second deadline dismisses it if the server is slow. Failed attempts without a usable snapshot can retry on the next launch.
- **Lazy timeline layout:** date boundaries, rather than a row for every photo, determine tile positions. Scrolling and scrubbing locate visible tiles by binary search; only tiles near the viewport are built, including in million-photo libraries. Timeline paths are resolved only when opening a photo or performing a file action, avoiding whole-library background path lookups and repeated rebuilds.
- **Incremental refresh:** while actively browsing, ncloud checks the account root's recursive WebDAV etag first. Unchanged trees skip photo-detail queries; Memories day counts are also checked at least every 15 minutes of active monitoring to catch delayed indexing. Changed trees invalidate reloadable memberships; edited cached days keep their photos visible and refresh as they enter the viewport, including same-count replacements. At the Timeline top, changed counts apply in place; while scrolled, a **↑ N new photos** pill avoids moving your place. A complete refreshed day replaces its old membership, including confirmed removals. Pull-to-refresh revalidates everything.
- **Optional push and idle behavior:** when Nextcloud Client Push (`notify_push`) is available, a secure same-origin WebSocket subscribes to changed file IDs and coalesces events. Push is a hint, not a durable change log: etag checks remain the fallback. Checks back off from one to five minutes after unchanged results; **after two minutes without interaction, all change-monitor timers and its socket stop**. Leaving the app stops them immediately. Touching/scrolling or returning resumes checking. Thumbnail prefetch and queued day loading pause while inactive; an already-started request can finish. No background wake lock or permanently running sync worker is used.
- **Smooth timeline:** with Memories, the timeline lays out every indexed day up front (placeholders sized from day counts), so scrolling never stops at the end of a loaded page. Only the days you scroll or scrub to are fetched, nearest first, in batches of about 200 photos; requests left behind by a fast scrub are dropped. Without Memories, near-bottom scrolling prefetches 200-item WebDAV pages. Pull-to-refresh keeps cached results visible; failures remain visible and stop automatic retries.
- **Unified cache:** Timeline, Albums, Shared and Drive reference one normalized on-device file store. Folders listed during album discovery open instantly in Drive, and favorites, moves, copies, renames, deletes, uploads and new folders patch the store so every view updates without reloading. Folder listings are reused for five minutes, or longer while the folder's etag is unchanged; refresh marks everything for revalidation while keeping it visible.
- **Memories:** detected automatically when installed and enabled for your account. The app reads lightweight day counts with preloading disabled, then requests complete days in batches (up to 1,500 photos on the Timeline, about 200 elsewhere). Actual DAV paths are resolved by file IDs in batches of at most **100**, respecting Nextcloud's search-comparison limit (larger batches caused HTTP 500). This never requires one metadata request per photo. Capture timestamps and camera-local calendar days come from Memories. **One exceptionally large day is loaded whole:** Memories has no within-day offset, so a 1,000-photo day can exceed the batch target. Your server must finish Memories indexing before all photos/albums appear; an empty index is not replaced with an expensive full-drive scan.
- **Smart albums:** walking down from your photo source, the **first folder containing photos/videos** on each branch becomes an album and includes everything beneath it. For example, `Photos/Travel/Japan/Kyoto` appears as **Kyoto** when Travel and Japan only contain subfolders. Grouping folders without direct media are not albums; empty and document-only branches stay hidden. Files are never moved or duplicated.
- **Section-based Albums:** Google Photos-inspired overview with a small **Pinned** row (Favorites, Offline, Bin), then separate **Smart albums**, **Shared with you** and **Nextcloud albums** cover previews. Shared is a proper album section, not a top shortcut. Each preview is limited to eight cards; **View all** or tapping its heading expands only that section into a full grid. Tapping a cover opens its photos; Back returns to the expanded section (Shared returns to its full grid), then the overview. Source and sorting stay in View options. Pinned shortcuts are fixed in this preview; there is no device-library or AI section.
- **Nextcloud theme:** a blue palette seeded from Nextcloud's `#0082C9`, with accessible light/dark foreground and container variants. Photo colors remain unchanged.
- **Compact dock:** a fixed compact floating dock where only the active destination shows its label. All destinations keep at least 48px tap targets. The active blue pill slides between tabs, with reduced-motion support. The viewer stays navigation-free.
- **Hot album catalogue:** Smart/native and incoming-shared album metadata restores independently in the background at account startup or sign-in, so opening Albums joins the existing loads instead of starting another. Cached cards remain intact during refresh, then update as a complete snapshot. After the 15-minute catalogue freshness window, a matching source-folder etag reuses Smart albums without repeating the folder walk; native album memberships revalidate separately. Opened Smart albums also retain their folder etag, avoiding day/detail/path requests when an expired cached membership is unchanged. Servers without etags retain time-based revalidation and explicit refresh always reloads.
- **Shared with you:** a dedicated album-cover section for incoming shared folders containing photos/videos. Outgoing shares, single-file shares, duplicate or overlapping incoming mounts and media-empty folders do not appear. Each card opens its folder recursively through paged DAV search, without scanning the entire account or requiring a recipient Memories index. Its catalogue also restores from disk and is reused for 15 minutes. Demo mode has no incoming shares.
- **Photo source:** Albums defaults to `Photos` when present, otherwise your drive root. Use **View options → Choose photo source** to choose a different root; the choice is stored securely with your account. The source is a wrapper, not a catch-all album. Loose media appears separately as **Photos at root**, containing only files directly in that source; folder albums remain visible and do not overlap with it. The timeline remains account-wide.
- **Nextcloud albums:** a separate section shows owned and shared albums from the Nextcloud Photos WebDAV API, preserving their names and membership, including empty native albums. These are not inferred from folders. Servers without this API still support Smart albums. External album members can be viewed/downloaded but are intentionally view-only in ncloud; album creation, membership edits and collaboration remain in Nextcloud.
- **Collections inside Albums:** Favorites, Shared (photos under paths you have shared), Offline originals and Recently deleted. Settings and cache management are under the profile avatar. Offline originals can be saved from file menus or the video player and survive browsing-cache eviction and clearing.
- **Drive:** keeps the exact server folder hierarchy, including empty folders, with breadcrumbs, upload/create and file actions. Both network responses and cached folder memberships must contain unique direct children of the requested path. Invalid disk snapshots are reloaded even when their saved etag matches. Folder cache keys contain no null bytes, since iOS SQLite text bindings truncate at the first null byte and would otherwise merge different folders. The corrected metadata format rebuilds the browsing catalogue on upgrade without touching server files or saved offline originals.

No custom backend or AI service is required. Servers without the Memories endpoint fall back to 200-item WebDAV SEARCH pages and modification dates; authentication, server and malformed-response errors are surfaced rather than silently falling back.

### Streaming and local cache

- **Instant video streaming** with buffering indicator, scrubbing, mute and optional save-offline replay.
- **Bounded browsing storage**: thumbnails (including viewer previews), loaded media pages/cursors, Drive listings and library/album/People metadata share one **500 MiB** disk budget. On overflow, the oldest entries are evicted down to 80% to avoid constant cleanup. Fresh pages are reused; stale content remains visible during refresh. Settings → Offline cache reports and clears browsing storage, not saved originals. Device cache cleanup can also remove browsing data.
- **Local database**: metadata uses normalized, account-scoped SQLite file records and ordered listing memberships, with queryable file fields, schema migrations and incremental transactions instead of rewriting the full library. Change detection marks cached folder/view memberships stale rather than deleting them, keeping cached photos available while changes revalidate, including after restart. Disk records survive the bounded in-memory store's eviction; restores and listing hydration are limited to 40,000 files. Legacy JSON/gzip migrates lazily. New metadata uses database normalization rather than repeated JSON compression; already-compressed thumbnails and saved originals are not recompressed.
- **Android database compatibility**: row-returning SQLite configuration statements use the query API, not Android's execute-only API. This fixes a database-opening failure reported as `SQLite 0`; upgrading retries normal initialization without requiring a cache reset or deleting saved originals.
- **Metadata priority**: thumbnails leave up to **16 MiB** of headroom inside the shared browsing budget. On actual device-storage exhaustion, database writes and offline-membership saves reclaim the oldest thumbnails/viewer previews and retry, with at most three progressively larger reclamations. Saved originals and existing metadata are never deleted to recover a failed metadata write. If nothing reclaimable remains, the failure stays explicit and unsaved library changes remain pending; database errors identify the SQLite code rather than always blaming storage.
- **Low-write storage**: SQLite allocation (including WAL/SHM) and thumbnails share the 500 MiB budget. Unchanged library records do not produce database updates. Cache size accounting is incremental, maintenance runs only under storage pressure rather than on a timer, and thumbnail access timestamps are throttled to reduce disk writes. Storage recovery only runs during a failed operation, never as an idle retry loop.
- **Explicit offline storage**: Save offline keeps full originals and their membership in separate app-support storage with **no app-imposed cap** (device free space still applies). These files survive browsing-cache clearing and upgrades from the previous originals cache. Disconnect removes both browsing storage and app-managed offline downloads, but not files exported elsewhere.
- **No automatic original downloads**: scrolling and opening photos request previews only, with no small-original fallback. Missing previews require a working server preview provider or an explicit original-download action. Videos stream through the native player unless saved offline; native buffering is platform-managed and is not guaranteed RAM-only.
- **On this day** from loaded photos using Memories capture days (modification dates without Memories), a draggable loaded-date scrubber and **pinch to change grid density** (2–6 columns).

### Android Folder sync

Open **profile avatar → Your space → Folder sync → Add folder**. Manually choose a device folder using the system picker, then your existing Nextcloud destination. Nothing is prefilled or added automatically. The visual folder preview shows exactly where uploads go; saved pairs can be edited or removed under **More options**.

- **Selected folders only on Android**: no photo-library permission, camera preset or automatic source selection. Android requests access only to the folder you explicitly select; supported locations depend on the system picker. iOS whole-album backup is a separate, explicitly selected source described below, not a restoration of the obsolete photo-sync implementation.
- **Inclusions/exclusions**: select included subfolders and excluded subfolders visually, with full relative paths. Selecting a parent includes/excludes its descendants and future files. File types can be all files, photos, videos, or both, using provider MIME types and recognized extensions when a provider supplies no specific type. Exclusions win. Rules apply in both transfer directions. Files already uploaded or downloaded are never removed when rules change; receipts remain so restoring an inclusion does not reupload unchanged confirmed files. Existing saved pairs default to all files, no exclusions.
- **Parallel uploads**: new pairs default to three upload lanes; choose one, two or three in **More options**. Original staging, transfer and confirmation are bounded by that limit. Destination folder creation is serialized and filenames are reserved across lanes to avoid internal races; uploads remain conditional create-only. On failure, already-started transfers settle and checkpoint before the run returns. More lanes can improve throughput but are not a server-independent speed guarantee.
- **Background uploads**: opt into **Continue in background** and allow notifications. An Android `dataSync` foreground service retains the running UI engine with a visible **Pause** notification for manually started transfers. Without this option, leaving ncloud pauses subsequent files. Notification permission is requested only through explicit user action.
- **Scheduled backup (Android 6 / API 23+)**: choose **Scheduled backup** when adding/editing an upload-only folder: interval (at least 15 minutes), daily local time, or weekly weekday/time. Default is **Off · manual only**. This replaces the old foreground-only repeat timer; old repeat flags do not silently enable unattended work. Allow notifications using the schedule's permission button. Android WorkManager can start a separate headless engine after the UI closes and reschedule work after reboot, with a persistent backup notification. It checks due work approximately every 15 minutes; this is **best effort, not an alarm**. Battery restrictions, Doze, charging/network conditions and OS quotas may delay it. Force-stop prevents work until ncloud is opened again. The folder card shows due time and persisted progress/results; **Pause scheduled run** stops the current run while retaining future occurrences. Disable the schedule, edit/remove settings, or sign out to cancel registrations. Sign-out suspends the account; reconnecting the account reconciles its saved schedules and preserves receipts.
- **Calendar/missed-run policy**: daily/weekly schedules use the device's current timezone, recomputed on each worker check. DST gaps use the platform's normalized local time; repeated hours share one wall-date occurrence. Already completed dates/interval slots are not replayed after clock reversal. Missed occurrences coalesce into the latest slot, not a backlog. Only success consumes a slot; interrupted/failed runs retry on a later check using existing receipts. Editing the schedule creates a new revision and starts its new calendar from the edit time.
- **Scheduled execution safety**: a native, account-scoped OS file lock excludes simultaneous manual/headless runs across Flutter engines and processes, without an expiring lease. Process death releases it. Workers load the current account from encrypted secure storage; job payloads contain only pair/revision IDs, never credentials. The local `ncloud_folder_access` FlutterPlugin auto-registers SAF operations in every engine and explicitly refuses picker UI without an activity. Workers verify their own foreground notification before any folder/network transfer, failing visibly rather than accepting Workmanager's regular-worker fallback if foreground startup fails. Workers reuse the create-only transfer engine, rules, receipts, and SQLite journal. Actual Wi-Fi transport (not merely unmetered connectivity) and charging are checked before scanning and every transfer. Already-started files may finish after a condition changes.
- **Settings recovery**: database loading and Android job registration failures identify the failing operation, with an in-screen retry. They never reset saved pairs or transfer receipts. SQLite configuration statements that return rows use the query API, as required by Android's database driver.
- **Limits/checkpoints**: workers request a stop after eight minutes, close their independent HTTP client on cancellation, and poll persisted cancellation/progress every two seconds. WorkManager's stop callback records interruption before engine teardown. Current provider operations settle before releasing the account lock; the OS can terminate work sooner. File receipts checkpoint individually; interrupted originals restart in full. A crash between transfer and receipt may preserve an extra cloud copy, never overwrite/delete an original. Manual background runs retain their existing six-hour service safety limit.
- **Safety**: the create-only engine preserves existing cloud names and never changes or deletes device originals. Conflicting filenames receive separate cloud copies, not an unsafe filename/size-based deduplication. Per-file receipts skip confirmed unchanged uploads on later runs and after restart. Choosing another destination resets that pair's history, not files in the old destination, and may copy originals again. Overlapping cloud destinations are rejected.
- **Scope**: the rules editor and interval/daily/weekly schedule editor are Android-only. The `BackupSchedule`, `BackupScheduler`, `HeadlessBackupRunner` and `SyncRunLock` interfaces also support the separate iOS whole-album adapter. Workmanager 0.10.10 supports Flutter 3.38.5, Android API 23+, and iOS 14+.

### iOS whole-album backup

Open **Folder sync → Add sync pair → Apple Photos album**, choose an entire album and a cloud destination, then save. Individual assets cannot be selected here; Files folders remain a separate manual source. Backup is upload-only and off by default until you either tap **Sync now** or explicitly enable **Automatic album backup**. The destination includes the selected album name, for example `/Backups/Trips/…`. Multiple albums can share a parent destination when their actual destination folders do not overlap.

- **Permissions and originals**: whole-album backup requires **Full Access** to Photos; Limited Access is rejected rather than silently backing up only a subset. Nothing requests Photos permission until you choose the album source. User albums, Recently Added, and Favorites are offered explicitly, never preselected. PhotoKit exports original HEIC/JPEG/RAW/video resources and Live Photo still/video components without re-encoding. Stable asset/resource filename suffixes distinguish repeated camera filenames. Photos/iCloud materializes originals on demand; staging requires enough free device space.
- **Recurrence and OS limits**: automatic pairs check approximately every 15 minutes while ncloud is open and immediately when it resumes. A single registered `BGProcessingTask` requests additional background opportunities; **iOS decides timing and duration**, not a guaranteed 15-minute background schedule. Background App Refresh, power restrictions, usage patterns and force-quitting can prevent execution. Enable Background App Refresh and reopen after force-quitting. Files-provider folders are still manual-only.
- **Safety and recovery**: foreground and background engines share a native account file lock, the create-only engine and per-file SQLite receipts. Every export rechecks current album membership and resource revision, before and after the iCloud download; unknown original sizes are accepted only from revisioned Photos resources, then the exact staged byte count is confirmed remotely. Removed members never delete cloud files. Edited originals preserve earlier cloud copies. Permissions, missing albums, changed resources, iCloud errors and rejected scheduling remain explicit. Native exports time out without publishing partial files; interrupted uploads retry from the last confirmed file, not byte offsets.
- **Controls**: edit a pair to disable automatic backup, use **Pause current background run** to stop the current opportunity, or remove settings/sign out. These do not delete originals. The next background opportunity is submitted before transfers so OS termination does not silently remove recurrence. A locked Keychain leaves another opportunity pending and records an error for the next open; background jobs always reload and validate the current account and saved settings, never stored credentials in an OS payload.

### Non-destructive custom folder sync

For a custom device folder choose **Folder sync → Add folder** on Android, or **Files folder sync** on iOS. Select the device folder and existing Nextcloud destination. **Backup (device → cloud)** is the default; Download and Two-way, keep both remain in Android **More options**. Folder names default to the selected device folder rather than requiring extra setup text.

**The selected device folder itself is included for Backup and Two-way.** Selecting `Documents` with cloud location `/Backups/Phone` produces `/Backups/Phone/Documents/...`, preserving subfolders rather than placing its contents directly in `/Backups/Phone`. The selected root is created even when empty. Download-only pairs still read the exact selected cloud folder into the device folder. Existing pairs use the corrected named root on their next run; previously uploaded flattened files are **not moved or deleted**, so this can leave an additional preserved copy. The pair card shows the actual cloud root.

- **Never a deletion mirror**: the engine has no remote delete, overwrite or move operation. Existing names receive separately named copies, including changed files. Conditional create-only uploads and exclusive local creation reject destination races. Two-way is an additive merge, not a byte-for-byte mirror. A first run against populated folders can create duplicates; it does not guess equality from size alone.
- **Android**: persisted Storage Access Framework folder grants, optional scheduled upload-only backups and opt-in continued manual background transfers, as described above.
- **iPhone/iPad Files**: selected Files-provider folders with saved security-scoped bookmarks. Tap **Sync now** again whenever needed; this is reusable, not a single-use import. Providers can revoke or invalidate access; **Reconnect device folder** reselects the same source while retaining history. Access, writable locations and iCloud materialization depend on the provider. Automatic iOS runs apply only to explicitly selected Apple Photos albums, not Files folders.
- **Battery/network**: Wi-Fi only defaults on; charging-only is optional. Conditions are checked before each transfer; already-started files may finish after conditions change. Pausing stops subsequent files; leaving the app does so unless Android background uploads were explicitly enabled. Enabled Android schedules use constrained, OS-managed workers rather than a foreground timer.
- **Android sync recovery**: Wi-Fi/charging checks are routed separately from folder selection. **Sync now** reuses the saved folder grant and never opens a permission picker; **Reconnect device folder** is only for revoked access. Missing native services, denied folder access, unavailable files, transfer I/O and sync-journal failures show distinct guidance rather than a generic storage/connection warning.
- **Persistence**: account-scoped pairs and file-version receipts live in a separate app-support SQLite journal, outside the disposable browsing cache. A run inventories both sides before transferring; permission/listing failures stop safely. Completed files are checkpointed individually. An interrupted file restarts in full; chunk-resume is not implemented. A crash between transfer and receipt may create an extra preserved copy on retry.
- **Storage/safety**: each upload lane stages one original in temporary device storage and removes it after transfer (up to three originals with parallel uploads). Downloads remain serial. Large files need free space; process termination may leave a temporary staging file. Interrupted staging older than 24 hours is reclaimed when preparing another transfer. Sync-created destination files are not part of the 500 MiB preview cache and are never evicted by cache clearing. Removing a pair removes only settings/history, not either folder; recreating a pair can duplicate files. Disconnect suspends schedules but retains account-scoped receipts for future reconnection. There is no Move-to-cloud or local-original deletion in this feature.
- Avoid overlapping folder pairs or selecting a provider already mirroring the same Nextcloud folder. Exact duplicate device selections and overlapping actual cloud destination roots are rejected. Scans are bounded to 100,000 files per side and 64 levels; unsupported names, symlinks, absent file dates/revisions or exceeded limits stop explicitly rather than skipping silently. Files-folder change detection uses size/modification date; Photos uses asset/resource revisions and cloud files use etags.

## Available features

System light/dark themes and a black distraction-free viewer are supported.

| Surface | Available now |
|---|---|
| Timeline | Day/month grouping, date jump/scrubber, photo/video/favorite filters, name filtering, sorting, automatic pagination beyond 200 items |
| Albums | Parent Smart albums, expandable section previews, recursive media browsing with subfolder filters, native Nextcloud albums, pinned shortcuts |
| Drive | Separate file/folder list, breadcrumbs, sorting, multi-file upload and per-item actions |
| Viewer | Swipe between photos, pinch/double-tap zoom, hide controls, slideshow, favorite, delete, original export and in-app video playback |
| Organize | Long-press selection, select a day, bulk favorites/move/copy/delete, rename, destination-folder picker, overwrite protection |
| Share | List/create/revoke read-only public links, optional password and expiry, copy or system share; folders can be shared as albums |
| Recovery | Nextcloud trash listing and restore to original location (requires server trash app) |

Smart albums are warmed independently at startup: one Memories subfolder request supplies immediate parents and recursive indexed covers. Parents with no indexed preview are hidden; there is no descendant walk or per-child direct-media query. A direct-media check at the source adds **Photos at root** without suppressing any parents. Opening that one album uses nonrecursive Memories day queries or DAV depth-one SEARCH; all other folder albums remain recursive. Without Memories, a depth-one source listing plus one recursive `SEARCH limit=1` cover lookup per immediate folder establishes nonempty parents without enumerating their entire photo lists. The Smart/native catalogue and resolved default source are cached for 15 minutes, independently of photo pages; the default source hint remains until cache invalidation. Refresh replaces the full catalogue atomically. Incoming shared albums use OCS `shares?shared_with_me=true` and recipient-visible `path` values, plus one scoped media-cover search per incoming folder; they never use the outgoing-share list or a whole-account photo filter. Native albums use Nextcloud Photos' `/remote.php/dav/photos/{user}/albums` and `sharedalbums` collections; their membership is returned as a whole by that API. Drive remains the complete file view.

Selection operations run sequentially and report how many completed if a later item fails; they are not atomic. Deletion affects server originals and folder contents, not just the current view. Trash recovery depends on server configuration/retention. Nextcloud handles restore conflicts by choosing a new name; if the original folder is unavailable, it may restore to your root folder. There is intentionally no permanent-delete or empty-trash button in this preview.

Videos **stream immediately** from WebDAV through the native player (ExoPlayer/AVPlayer) with the Authorization header kept in request headers, never in the URL. The viewer shows buffering, elapsed/total time, scrubbing and mute. **Save offline** keeps a full copy in separate persistent app storage so later replays work without network; offline copies are used automatically. Codec support follows the device; if streaming fails, save offline or export the original. Slideshows operate on the loaded viewer collection and pause when the app backgrounds. Demo videos are illustrations, not playable files.

**Still not full non-AI Immich parity:** automatic camera backup/background queues, two-way folder sync, maps, editing, Live Photos, archive/locked folders, partner libraries, shared-album collaboration/comments, and account switching remain future work. Memories supplies capture-date indexing; ncloud does not run its own indexer. There are no fake controls for missing capabilities. AI/face/semantic features are excluded from this milestone.

## Foundation capabilities

| Area | Preview functionality |
|---|---|
| Experience | Material 3, system light/dark theme, responsive photo grid, local demo |
| Account | Nextcloud Login Flow v2, app-password alternative, secure credential storage, session restore, disconnect |
| Files | Folder browsing/breadcrumbs, create folder, streamed foreground upload, download original via the system share/save sheet |
| Photos | Memories capture-date browsing with on-scroll day batches; paged modification-date WebDAV fallback, server thumbnails, swipe/zoom viewer |
| Favorites | Favorite files and folders, server-wide paginated favorites view |
| Filtering | Case-insensitive name filtering of loaded items/current folder, pull-to-refresh |

Photos use the installed Memories index and standard Nextcloud WebDAV, not an Immich API. Previews depend on your server's preview providers (especially HEIC and video); unavailable previews have a retry state. API errors are displayed, never replaced with fake demo data. Refreshing restarts a listing; concurrent index/file changes can shift batch boundaries. Name search, sort, filters, date jumps and slideshows operate on loaded items, not the entire remote library.

Single-thumbnail requests are limited to four concurrent transfers; Memories multipreview requests batch up to 48 previews. Grids request 384px previews and the viewer requests 1280px, with bounded decoding, a 64 MiB/4,000-entry encoded in-memory LRU cache and the persistent disk cache described above. Transient server overload is retried once; failed requests are not permanently cached. Images and video posters require working Nextcloud preview providers; missing previews never trigger automatic original downloads. The cache speeds up browsing; it is not two-way offline sync.

Regular transfers require the app to stay open; Android Folder sync can opt into a foreground service to continue an already-started run in the background. Uploads never overwrite existing filenames. Folder sync checkpoints completed files; there is no unattended/chunk-resumable transfer queue yet. Regular Download & share transfers stream to temporary app storage and open the system share sheet; folder-sync downloads instead go to the explicitly selected folder. Disconnect removes credentials and ncloud's downloaded cache, but not files saved in paired folders or shared elsewhere. Revoke the app password in Nextcloud Security settings to revoke server access.

## Architecture and APIs

`lib/models.dart` contains typed account/file/share/trash models and URL validation. `nextcloud_client.dart` handles Login Flow v2, OCS user lookup (DAV user ID may differ from login email), WebDAV listing/search/transfers/organization, sharing links, trash restore and authenticated previews. `app_controller.dart` coordinates session storage, race-safe paged loading, demo data, and foreground transfers. `library_screen.dart` implements the four-space UX; `asset_viewer.dart` handles viewing/video/slideshows; `library_actions.dart` contains shared actions and destination/share/trash/account surfaces. `screens.dart` contains sign-in and shared forms.

Credentials use iOS Keychain / Android encrypted storage. HTTPS is required, authenticated redirects are not followed, and login endpoints must remain on the configured origin. No certificate bypass, main-password persistence, analytics, or third-party image service is used. Explicit offline originals stay in app-support storage until disconnect or uninstall; share/save transfers use temporary storage. Thumbnails are held in bounded memory and disk caches.

## Roadmap toward the full vision

This is the foundation, not a claim that core Nextcloud supplies all Immich and Google Drive capabilities.

1. Backup hardening: stronger content deduplication, resumable/chunked uploads, OS background queues and recovery reporting beyond the current foreground, create-only backup.
2. Further Drive essentials: richer sharing permissions, offline files, server search, file previews/editing and multiple accounts.
3. Further photo library: Live Photos/RAW/HEIC handling, maps, collaborative libraries and duplicate management.
4. Intelligence: evaluate Nextcloud Photos/Memories/Recognize/Face Recognition APIs and compatibility. Face grouping, semantic search, memories and transcoding require suitable server apps or a separately designed indexing service; they cannot be promised from core WebDAV alone.
5. Distribution: production signing, TestFlight, app-store privacy disclosures, accessibility/device testing, and release hardening.

CI checks API contracts with mocked HTTP responses, scroll/widget flows, mobile UI captures, and a real isolated Nextcloud 32 instance with Memories installed and indexed (day summaries, indexed folders, batched DAV path resolution, capture metadata, plus the core file/native-album APIs). Live tests are skipped by default locally; they use only a disposable loopback HTTP fixture, while app sign-in requires HTTPS. This does not prove compatibility with every Nextcloud deployment. Expand the server-version matrix and add real-device background-lifecycle tests before production use.

CI reuses Flutter/Dart package caches plus Gradle dependencies, wrapper distributions and cacheable task outputs. Gradle build caching is enabled; pull requests can read but not write the Gradle cache. APKs are still compiled and signature-checked on every successful run, never reused as a cache shortcut. The build step skips redundant package resolution and reports its wall-clock duration in the Actions summary. Cold builds, dependency/toolchain changes and cache eviction remain slower; a one-minute release build is not guaranteed. Configuration caching is not enabled, to avoid assuming Flutter/plugin compatibility.
